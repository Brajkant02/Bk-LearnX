Relational Database Design

1. Relational Database Design

Relational Database Design का अर्थ है database की tables, attributes, keys और relationships को इस प्रकार design करना कि data accurate, consistent, efficient और easy to maintain रहे। एक अच्छे relational design में information को logical relations/tables में organize किया जाता है और unnecessary duplication को कम किया जाता है।

अगर एक ही table में बहुत अलग-अलग प्रकार की information store कर दी जाए, तो same information बार-बार repeat हो सकती है। इससे storage waste होने के साथ-साथ insertion, update और deletion के समय problems उत्पन्न हो सकती हैं। इन्हीं problems को कम करने के लिए Normalization का उपयोग किया जाता है।

Poorly Designed Relation ↓ Redundancy + Dependencies ↓ Insertion / Update / Deletion Anomalies ↓ Normalization + Decomposition ↓ Better Relational Design
Exam Definition:
Relational database design is the process of organizing data into related tables with appropriate keys, dependencies and constraints to reduce redundancy and maintain data integrity.

2. What is Normalization?

Normalization relational database को व्यवस्थित करने की एक systematic process है जिसमें tables को ऐसे structure में transform किया जाता है जिससे unnecessary data redundancy और undesirable dependencies कम हों तथा data integrity बेहतर हो। GeeksforGeeks के अनुसार normalization का मुख्य उद्देश्य redundancy को reduce/eliminate करना और insertion, update तथा deletion anomalies को avoid करना है।

Normalization में अक्सर एक बड़ी relation को smaller related relations में decompose किया जाता है। Decomposed tables को keys के माध्यम से आपस में relate किया जाता है। इससे प्रत्येक table एक specific fact या subject को represent करने के करीब आ जाता है।

Normal Forms का क्रम

1NF → 2NF → 3NF → BCNF → 4NF → 5NF

हर higher normal form पहले वाले normal form की conditions को satisfy करती है और उसके ऊपर additional restrictions लगाती है। सामान्य progression में 1NF atomic values पर focus करता है, 2NF partial dependency हटाता है, 3NF transitive dependency को address करता है, BCNF determinants को superkeys बनाता है, 4NF multivalued dependencies और 5NF join dependencies को address करता है।

Important: Normalization का उद्देश्य केवल "ज्यादा tables बनाना" नहीं है। मुख्य उद्देश्य logical structure improve करना, redundancy/anomalies reduce करना और data dependencies को properly represent करना है।

3. Purpose of Normalization

Normalization database design की quality improve करने के लिए किया जाता है। जब same fact कई rows में repeated होता है, तो future updates में inconsistency की possibility बढ़ती है। Normalization related facts को appropriate relations में separate करने में सहायता करता है।

Major Objectives

  1. Reduce Data Redundancy: Same information को unnecessary तरीके से बार-बार store करने से बचना।
  2. Prevent Update Anomalies: एक fact बदलने पर multiple rows में manual changes की आवश्यकता कम करना।
  3. Prevent Insertion Anomalies: किसी independent fact को store करने के लिए unrelated data की आवश्यकता न पड़े।
  4. Prevent Deletion Anomalies: एक record delete करने पर unrelated useful information accidentally delete न हो।
  5. Improve Data Integrity: प्रत्येक fact को appropriate place पर maintain करना।
  6. Improve Maintainability: Database structure को understand और maintain करना आसान बनाना।
  7. Reduce Inconsistency: Duplicate copies के बीच conflicting values की possibility कम करना।
  8. Create Logical Relationships: Tables के बीच proper keys और dependencies establish करना।
Exam Line: Normalization is used to reduce redundancy, eliminate undesirable dependencies and prevent insertion, update and deletion anomalies.

4. Data Redundancy

Data Redundancy का अर्थ है same piece of information का database में unnecessarily multiple times stored होना। थोड़ी controlled redundancy कभी-कभी performance या business requirements के लिए intentionally रखी जा सकती है, लेकिन unnecessary redundancy database design problem बन सकती है।

Example

StudentID StudentName CourseID CourseName Teacher
101 Amit C01 DBMS Dr. Rao
102 Neha C01 DBMS Dr. Rao
103 Rahul C01 DBMS Dr. Rao

ऊपर CourseName और Teacher की information प्रत्येक student row में repeat हो रही है। अगर C01 में 500 students हैं, तो वही course-related information 500 rows में repeat हो सकती है। यही redundancy का example है।

Problems Caused by Redundancy

  • Extra storage requirement।
  • Update के समय multiple rows change करनी पड़ सकती हैं।
  • एक row update और दूसरी row unchanged रहने पर inconsistency हो सकती है।
  • Insertion और deletion operations unnecessarily difficult हो सकते हैं।
  • Database maintenance complex हो सकती है।
Key Idea: यदि एक fact database में कई places पर stored है, तो उस fact को update करते समय सभी copies correctly update करना जरूरी हो जाता है।

5. Updating Anomalies

Poor relational design और excessive redundancy से data anomalies हो सकती हैं। Anomaly का अर्थ है database operation के दौरान unwanted inconsistency, data loss या unexpected restriction उत्पन्न होना। मुख्य तीन anomalies हैं: Insertion, Update और Deletion Anomaly.

1. Insertion Anomaly

जब किसी independent information को insert करना संभव नहीं होता क्योंकि table में किसी unrelated information की भी आवश्यकता पड़ती है, तो इसे insertion anomaly कहते हैं।

Example: यदि CourseID और CourseName को StudentEnrollment table में ही रखा गया है, तो नया course तब तक add करना difficult हो सकता है जब तक कोई student उस course में enroll न हो।

2. Update Anomaly

जब एक fact multiple rows में repeated हो और उसे update करने के लिए कई rows बदलनी पड़ें, तो update anomaly हो सकती है। यदि कुछ rows update हो जाएँ और कुछ नहीं, तो database inconsistent हो सकता है।

Example: किसी course के instructor का नाम 100 rows में stored है। Instructor का नाम बदलने पर सभी 100 rows update करनी पड़ सकती हैं।

3. Deletion Anomaly

जब किसी record को delete करने पर उस record के साथ unrelated but important information भी खो जाए, तो deletion anomaly कहलाती है।

Example: यदि किसी course की information केवल उसके last enrolled student के row में stored है और उस student को delete कर दिया जाए, तो course की information भी accidentally lost हो सकती है।

Anomaly Meaning Typical Problem
Insertion New fact insert करना difficult Unrelated data required
Update Same fact कई places पर update करना Inconsistent copies
Deletion Data delete करते समय useful fact भी lost होना Unintended information loss
Remember: Normalization anomalies को reduce करने का primary database-design technique है।

6. Functional Dependencies

Functional Dependency (FD) relation के attributes के बीच एक constraint है। यदि attribute/set of attributes X की value किसी attribute/set of attributes Y की value को uniquely determine करती है, तो हम लिखते हैं:

X → Y

इसे पढ़ते हैं: "X functionally determines Y". X को determinant कहा जाता है और Y dependent attribute कहलाता है।

Simple Example

मान लें StudentID हर student के लिए unique है:

StudentID → StudentName StudentID → Course

यदि StudentID = 101 है, तो उस ID से associated StudentName और Course uniquely determine किए जा सकते हैं।

Types of Functional Dependency

Trivial FD

जब Y, X का subset हो, जैसे {StudentID, Name} → Name।

Non-Trivial FD

जब Y, X का subset न हो, जैसे StudentID → StudentName।

Full Functional Dependency

Y पूरी composite key X पर depend करता है और X के किसी proper subset पर depend नहीं करता।

Partial Dependency

Composite key के केवल एक proper subset से non-key attribute determine हो जाए। यह 2NF में allowed नहीं है।

Transitive Dependency

जब X → Y और Y → Z होने के कारण X → Z indirectly प्राप्त होता है। 3NF का प्रमुख focus इसे remove करना है।

Candidate Key और Prime Attribute

Normalization समझने के लिए candidate key और prime attribute महत्वपूर्ण हैं। Candidate key वह minimal attribute set है जो relation के प्रत्येक tuple को uniquely identify कर सकता है। किसी candidate key का हिस्सा prime attribute कहलाता है। Candidate key का हिस्सा न होने वाला attribute non-prime attribute कहलाता है।

Normalization Connection:
2NF → Partial dependency नहीं
3NF → Transitive dependency नहीं
BCNF → हर determinant superkey होना चाहिए

7. Decomposition

Decomposition का अर्थ है एक large relation को दो या अधिक smaller relations में divide करना ताकि redundancy और undesirable dependencies को reduce किया जा सके। Normalization में decomposition एक fundamental operation है।

Example

मान लें:

ENROLLMENT(StudentID, StudentName, CourseID, CourseName, Instructor)

अगर dependencies हैं:

StudentID → StudentName CourseID → CourseName, Instructor

तो relation को logically split किया जा सकता है:

STUDENT(StudentID, StudentName) COURSE(CourseID, CourseName, Instructor) ENROLLMENT(StudentID, CourseID)

अब Student information और Course information एक ही बात को बार-बार store नहीं करतीं। Tables को keys के माध्यम से join करके combined information प्राप्त की जा सकती है।

Good Decomposition की Properties

  1. Lossless Join: Decomposed relations को join करने पर original information recover हो सके और spurious/lost information न आए।
  2. Dependency Preservation: Original functional dependencies को decomposed relations पर enforce करना possible हो।
  3. Reduced Redundancy: Repeated facts को appropriate relations में separate करना।
  4. Improved Integrity: Dependencies और constraints को clearer बनाना।
Exam Point: Normalization में decomposition करते समय केवल tables split करना पर्याप्त नहीं है; lossless join और dependency preservation जैसी properties भी important हैं।

8. First Normal Form (1NF)

1NF normalization का पहला level है। किसी relation को 1NF में होने के लिए प्रत्येक attribute में atomic (single-valued) value होनी चाहिए। Repeating groups, arrays या multiple values एक ही cell में नहीं होने चाहिए। GeeksforGeeks के अनुसार 1NF में columns atomic values रखते हैं और repeating groups नहीं होने चाहिए।

Rules of 1NF

  1. Each cell should contain a single value.
  2. Repeating groups नहीं होने चाहिए।
  3. Multi-valued attributes को अलग rows/relations में represent करना चाहिए।
  4. Rows को identify करने के लिए appropriate key होना चाहिए।

Not in 1NF

StudentID Name PhoneNumbers
101 Amit 9876..., 8765...

एक cell में दो phone numbers हैं, इसलिए यह atomic-value rule violate करता है।

Convert to 1NF

StudentID Name PhoneNumber
101 Amit 9876...
101 Amit 8765...

या practical relational design में Student और StudentPhone जैसी separate relations बनाई जा सकती हैं, depending on keys and requirements.

One-Line Rule: 1NF = Atomic values + No repeating groups.

9. Second Normal Form (2NF)

किसी relation के 2NF में होने के लिए वह पहले 1NF में होना चाहिए और कोई non-prime attribute composite candidate key के केवल एक proper subset पर depend नहीं होना चाहिए। इसे no partial dependency के रूप में याद किया जाता है।

Example

Relation:

ENROLLMENT(StudentID, CourseID, StudentName, CourseName, Marks) Key = (StudentID, CourseID)

Functional dependencies:

StudentID → StudentName CourseID → CourseName (StudentID, CourseID) → Marks

StudentName केवल StudentID पर depend कर रहा है, जबकि StudentID composite key का एक हिस्सा है। इसी प्रकार CourseName केवल CourseID पर depend कर रहा है। इसलिए partial dependencies मौजूद हैं और relation 2NF में नहीं है।

Decomposition

STUDENT(StudentID, StudentName) COURSE(CourseID, CourseName) ENROLLMENT(StudentID, CourseID, Marks)

अब StudentName StudentID पर depend करता है, CourseName CourseID पर depend करता है, और Marks पूरी composite key (StudentID, CourseID) पर depend करता है।

One-Line Rule: 2NF = 1NF + No Partial Dependency.

10. Third Normal Form (3NF)

3NF में relation को 2NF में होना चाहिए और non-prime attributes में undesirable transitive dependency नहीं होनी चाहिए। Standard 3NF condition को functional dependency X → Y के लिए इस प्रकार समझा जाता है: X superkey हो या Y prime attribute हो। citeturn0search2turn0search6

Transitive Dependency

मान लें:

StudentID → DepartmentID DepartmentID → DepartmentName Therefore: StudentID → DepartmentName

यहाँ DepartmentName directly StudentID की property नहीं है; वह DepartmentID के through determine हो रहा है। यही transitive dependency का example है।

Decomposition

STUDENT(StudentID, StudentName, DepartmentID) DEPARTMENT(DepartmentID, DepartmentName)

अब DepartmentName केवल Department table में stored है। Student table DepartmentID के माध्यम से Department से related है।

One-Line Rule: 3NF = 2NF + No Transitive Dependency for non-prime attributes.

11. Boyce-Codd Normal Form (BCNF)

BCNF (Boyce-Codd Normal Form) 3NF से stricter normal form है। BCNF में प्रत्येक non-trivial functional dependency X → Y के लिए X का superkey होना आवश्यक है। GeeksforGeeks के अनुसार BCNF का key test यही है कि हर determinant superkey होना चाहिए। citeturn0search5turn0search3

BCNF Rule

For every non-trivial FD X → Y: X must be a Superkey

BCNF उन cases में useful है जहाँ relation 3NF में होने के बावजूद कुछ redundancy functional dependencies के कारण बच सकती है, विशेषकर multiple candidate keys वाले complex designs में।

3NF vs BCNF

3NF BCNF
हर FD में X superkey हो सकता है या Y prime attribute हो सकता है। हर non-trivial FD में X superkey होना चाहिए।
Less strict More strict
कुछ special redundancy cases allow कर सकता है। Functional dependencies से होने वाली additional redundancy को अधिक strictly remove करता है।
One-Line Rule: BCNF = For every FD, determinant must be a superkey.

12. Multivalued Dependencies (MVD)

Multivalued Dependency (MVD) तब होती है जब एक attribute/set of attributes किसी दूसरे attribute के लिए multiple independent values determine करता है। इसे functional dependency से अलग समझना जरूरी है।

Notation:

X →→ Y

Example: Student, Hobby and Skill

मान लें एक student की multiple hobbies और multiple skills हैं और hobbies तथा skills एक-दूसरे से independent हैं। यदि दोनों को एक ही relation में रखा जाए:

STUDENT_INFO(StudentID, Hobby, Skill)

एक student की 2 hobbies और 3 skills होने पर combinations की multiple rows बन सकती हैं। इससे unnecessary repetition होती है।

StudentID Hobby Skill
101 Cricket Python
101 Cricket SQL
101 Cricket HTML
101 Music Python
101 Music SQL
101 Music HTML

यहाँ independent multi-valued facts एक ही relation में combine होने के कारण redundant combinations बन रहे हैं। ऐसे cases को 4NF decomposition से address किया जाता है। citeturn0search0turn0search4

Decomposition

STUDENT_HOBBY(StudentID, Hobby) STUDENT_SKILL(StudentID, Skill)
Remember: Functional Dependency → X → Y
Multivalued Dependency → X →→ Y

13. Fourth Normal Form (4NF)

4NF BCNF के बाद का normal form है और मुख्य रूप से Multivalued Dependencies से उत्पन्न redundancy को remove करने के लिए use किया जाता है। A relation 4NF में तब होती है जब वह BCNF में हो और उसमें कोई non-trivial multivalued dependency ऐसी न हो जिसका determinant superkey न हो। GeeksforGeeks 4NF को BCNF की extension के रूप में describe करता है जो independent one-to-many relationships की redundancy को address करता है। citeturn0search4turn0search3

4NF का Basic Rule

For every non-trivial MVD X →→ Y, X must be a Superkey

Example

Course के multiple instructors और multiple textbook authors हो सकते हैं और दोनों independent facts हैं:

COURSE(CourseID, Instructor, TextbookAuthor) CourseID →→ Instructor CourseID →→ TextbookAuthor

एक ही table में दोनों independent multi-valued relationships रखने पर instructor-author combinations repeat हो सकती हैं।

4NF Decomposition

COURSE_INSTRUCTOR(CourseID, Instructor) COURSE_AUTHOR(CourseID, TextbookAuthor)

अब प्रत्येक table एक independent multi-valued relationship को represent करती है और unnecessary combinations avoid होते हैं।

One-Line Rule: 4NF = BCNF + No problematic non-trivial Multivalued Dependency.

14. Fifth Normal Form (5NF)

5NF (Fifth Normal Form), जिसे Project-Join Normal Form (PJ/NF) भी कहा जाता है, normalization का अधिक advanced level है। इसका उद्देश्य ऐसी join dependencies से उत्पन्न redundancy को address करना है जहाँ relation को कई smaller relations में decompose करके ही proper structure प्राप्त होता है।

5NF में relation को ऐसी proper decomposition में further split नहीं किया जा सकता जिससे information loss के बिना join करके original relation recover न हो सके। GFG के normal forms reference में 5NF के लिए 4NF होना और further non-loss decomposition (join dependency) न होना key condition के रूप में दिया गया है। citeturn0search2turn0search6

Join Dependency का Concept

Join dependency का मतलब है कि किसी relation को कई projections/relations में split करने के बाद उन relations का natural join original relation को exactly reconstruct कर सके। यह concept complex many-to-many relationship designs में important हो सकता है।

General Example

मान लें किसी business relation में Supplier, Part और Project के बीच complex relationship है। यदि business rules यह बताते हैं कि valid combinations कुछ independent pairwise relationships से derive किए जा सकते हैं, तो single large relation में unnecessary combinations store हो सकती हैं। ऐसे case में appropriate decomposition करके Supplier-Part, Supplier-Project और Part-Project जैसे relations consider किए जा सकते हैं—लेकिन decomposition तभी सही है जब actual business rules उस join dependency को support करें।

Important: 5NF को केवल "table को और छोटे tables में तोड़ना" नहीं समझना चाहिए। यह join dependency और lossless reconstruction से संबंधित advanced normalization concept है।
One-Line Rule: 5NF = 4NF + no further non-loss decomposition caused by join dependencies.

15. Complete Normalization Process — Step by Step

किसी relation को normalize करते समय normal forms को क्रम से check किया जाता है। GeeksforGeeks के normalization guidance के अनुसार highest normal form determine करते समय 1NF → 2NF → 3NF → BCNF sequence में dependencies और keys check करना useful approach है। citeturn0search9

Step 1 — Identify Attributes and Keys

Relation के सभी attributes identify करें और candidate keys/primary key determine करें। Prime और non-prime attributes भी identify करना useful है।

Step 2 — Check 1NF

Check करें कि प्रत्येक cell atomic है या नहीं। Repeating groups और multi-valued attributes को remove करें।

Step 3 — Check 2NF

अगर key composite है, तो देखें कि कोई non-prime attribute key के केवल एक part पर depend तो नहीं कर रहा। यदि है, तो partial dependency remove करके decomposition करें।

Step 4 — Check 3NF

Transitive dependencies identify करें। Non-prime attribute किसी दूसरे non-key attribute के through determine हो रहा हो तो appropriate decomposition करें।

Step 5 — Check BCNF

हर non-trivial FD X → Y के लिए check करें कि X superkey है या नहीं। यदि determinant superkey नहीं है, तो BCNF violation है और decomposition की आवश्यकता हो सकती है।

Step 6 — Check Multivalued Dependencies

Independent multi-valued relationships identify करें। यदि problematic MVD है, तो 4NF decomposition consider करें।

Step 7 — Check Join Dependencies

Advanced designs में check करें कि relation को further lossless decomposition की आवश्यकता है या नहीं। यदि join dependency के कारण redundancy बची है, तो 5NF consider किया जा सकता है।

Identify Keys & FDs ↓ Check 1NF ↓ Remove Partial Dependencies → 2NF ↓ Remove Transitive Dependencies → 3NF ↓ Check Determinants → BCNF ↓ Check MVDs → 4NF ↓ Check Join Dependencies → 5NF

Mini Worked Example

Initial relation:

ENROLLMENT(StudentID, StudentName, CourseID, CourseName, Instructor, Marks)

Dependencies:

StudentID → StudentName CourseID → CourseName, Instructor (StudentID, CourseID) → Marks

Step A: Composite key = (StudentID, CourseID)

Step B: StudentName depends only on StudentID → partial dependency.

Step C: CourseName and Instructor depend only on CourseID → partial dependency.

Decompose:

STUDENT(StudentID, StudentName) COURSE(CourseID, CourseName, Instructor) ENROLLMENT(StudentID, CourseID, Marks)

अब each fact को appropriate relation में रखा गया है। Further normalization check करने के बाद यदि कोई transitive dependency या other violation नहीं है, तो design higher normal forms तक जा सकता है।

16. Normal Forms — Complete Comparison

Normal Form Main Condition Primary Problem Addressed
1NF Atomic/single-valued attributes; no repeating groups Repeating/multi-valued data
2NF 1NF + no partial dependency of non-prime attributes on part of a candidate key Partial dependency
3NF 2NF + no problematic transitive dependency; X superkey or Y prime for every non-trivial FD Transitive dependency
BCNF Every non-trivial FD determinant is a superkey Remaining FD-based redundancy
4NF BCNF + no problematic non-trivial MVD with non-superkey determinant Multivalued dependency
5NF 4NF + no further non-loss decomposition caused by join dependencies Join dependency

Easy Memory Trick

1NF → Atomic 2NF → Partial Dependency Removed 3NF → Transitive Dependency Removed BCNF → Determinant = Superkey 4NF → MVD Removed 5NF → Join Dependency

Normalization vs Denormalization

Normalization redundancy और anomalies reduce करने के लिए tables को logically decompose करती है। इसके opposite, denormalization, कुछ cases में performance/read efficiency के लिए intentionally redundancy introduce कर सकती है। इसलिए real-world design में normalization और performance requirements के बीच balance करना पड़ सकता है।
